# ADR-0004: v0.3 のパラメトリック多相・単一化・値の表現

* Status: Accepted
* Date: 2026-09-24

## Context

v0.2 で単相の代数的データ型と `match` 式を導入した（ADR-0003）。
ADR-0001 の Development Policy では、その次の段階を「型変数、パラメトリック多相、単一化」としている。
ADR-0003 の Consequences でも「型パラメータがないので、`Option[T]` のような汎用の型は書けず、要素型ごとに型を宣言する必要がある」と予告した。

この段階に進むには、v0.2 にはない次の点を決める必要がある。

* 型パラメータの宣言と、型の適用（`Option[Int]`）の具体構文
* 呼び出し時の型引数を、利用者に書かせるか、コンパイラが決めるか
* 型引数を決める仕組み（単一化）の範囲と、決まらなかったときの扱い
* 関数の引数と戻り値の型注釈を、引き続き必須にするか
* 多相な関数とデータ型の値を、IR と WebAssembly でどう表現するか
  v0.2 の IR は値ごとに `ValType`（`Int` = `i64`、`Bool`・関数値・データ型の値 = `i32`）を持つ（ADR-0002、ADR-0003）。
  型パラメータ `T` の値は、呼び出しによって `i64` にも `i32` にもなる。

本 ADR でこれらを決める。実装の詳細は `docs/design/v0.3-*.md` に書く。

## Decision

### v0.3 の範囲

v0.3 では、トップレベルの関数宣言と `type` 宣言に型パラメータを付けられるようにし、呼び出し側の型引数を単一化で決める。

```text
type Option[T] =
    | None
    | Some(T)

type List[T] =
    | Nil
    | Cons(T, List[T])

fn map[T, U](xs: List[T], f: T -> U) -> List[U] {
    match xs {
        Nil => Nil,
        Cons(x, rest) => Cons(f(x), map(rest, f)),
    }
}
```

v0.3 に含めないもの:

* let 多相。`let` で束縛した値の型は単相のままとする（後述）。
* 関数の引数と戻り値の型の推論。これまでどおり型注釈を必須とする。
  let 多相と Hindley–Milner 型推論は、ADR-0001 の成長過程のとおり次の段階で扱う。
* 呼び出し時に型引数を明示する構文（`identity[Int](1)`）。後述の理由で導入しない。
* 匿名関数の型パラメータ（`fn[T](x: T) -> T { x }`）。匿名関数は多相にできない。
  ただし、外側の関数の型パラメータは匿名関数の型注釈に書ける。
* 型パラメータへの制約（type class、trait、境界）。型パラメータの値に対してできることは、受け取る・渡す・返す・データ型に格納する、だけとする。
* 型パラメータを取る型パラメータ（高カインド型、`F[T]` の `F`）。
* 組み込みの `List` / `Option` と prelude。利用者が `type List[T] = ...` を宣言する。
  組み込みにするかどうかは、ADR-0003 で先送りした String / List の ADR で決める。
* `main` の型は v0.1 と同じ `() -> Int` とする。

### 具体構文

* 型パラメータは、宣言の名前の直後に `[T, U]` と書く。
  * 関数: `fn name[T, U](params) -> Type { ... }`
  * データ型: `type Name[T, U] = | Ctor(T) | ...`
* 型の適用は `Option[Int]`、`Pair[Int, Bool]`、`List[List[T]]`、`Option[Int -> Int]` と書く。
  `Option[Int] -> Int` は `Option[Int]` を受け取る関数型である。
* `[` と `]` をトークンとして追加する。v0.2 までは式にも型にも `[` がなかったので、既存の構文と衝突しない。
  ADR-0001 の例（`fn identity[T](x: T) -> T`、`type Option[T]`）の書き方をそのまま採用する。
* 型パラメータの名前は、型名や構築子名と同じく ASCII の大文字で始める。そうでなければ構文エラーとする。
* 型パラメータのリストは 1 つ以上の名前を持つ。`[]` と末尾の `,` は構文エラーとする（引数リストと同じ）。
* 式の中で名前の直後に `[` を書くと、「明示的な型引数は v0.3 では書けない」という構文エラーにする。

### 型パラメータの規則

* 関数の型パラメータのスコープは、その関数の引数の型、戻り値の型、本体（`let` の型注釈と匿名関数の型注釈）とする。
* データ型の型パラメータのスコープは、その型の構築子のフィールドの型とする。
* 型パラメータの名前は、`Int`、`Bool`、宣言したデータ型の名前と重複できない。同じリストの中で重複もできない。
* 関数の型パラメータは、引数の型か戻り値の型に 1 回以上現れなければならない。
  現れない型パラメータは、どの呼び出しでも型引数を決められないので、宣言の時点でエラーにする。
  データ型の型パラメータは、構築子のフィールドに現れなくてもよい（幽霊型を許す）。
* 型の適用では、型引数の個数が宣言の型パラメータの個数と一致しなければならない。
  `Option` だけ、`Int[Bool]`、型パラメータへの適用 `T[Int]` はエラーとする。
* 型パラメータの値は `==` / `!=` で比較できず、`match` で照合できない。
  値の中身を調べる方法がないことが、パラメトリック多相の性質（パラメトリシティ）の表れである。
* `main` は型パラメータを持てない。

### 型検査: 硬い型変数、単一化変数、単一化

型検査では、型変数を 2 種類に分ける。

* **型パラメータ（硬い型変数）**: 宣言に書いた `T`。宣言ごとに別のものとして扱い、自分自身とだけ等しい。
  多相な関数の本体は、型パラメータを具体的な型に置き換えずに 1 回だけ検査する。
* **単一化変数**: 多相な関数や構築子を参照するたびに、その型パラメータごとに新しく作る、まだ決まっていない型。

多相な名前（型パラメータを持つ関数、多相なデータ型の構築子）を式の中で参照すると、型パラメータを新しい単一化変数に置き換えた型（インスタンス化した型）がその式の型になる。
型が一致すべき場所（引数と引数の型、`if` の両分岐、`match` の各アーム、型注釈）では、`Equal` による比較の代わりに**単一化**を行い、単一化変数に型を割り当てる。

* 単一化は、トップレベルの関数 1 つの本体（その中の匿名関数を含む）の全体で行う。
  関数の引数と戻り値には型注釈が必須なので、単一化変数が関数の外に漏れることはない。
* 単一化は出現検査（occurs check）を行う。`?T` と `?T -> ?T` のような無限の型を作る単一化は失敗させる。
* 型引数は、引数だけでなく期待される型からも決まる。
  `let x: Option[Int] = None` の `None` や、`Option[Int]` を受け取る関数に渡した `None` は、型注釈や引数の型から `Option[Int]` に決まる。
  `let x = None` の後で `x` を `Option[Int]` として使えば、その使い方から決まる。

関数の本体を検査し終えた時点で、決まっていない単一化変数が残っていればエラーとする（「型引数を推論できないので型注釈を付けてほしい」というメッセージ）。

* 例: `let x = None` だけを書いて `x` を使わない場合や、`length(Nil)` のように、どこからも要素型が決まらない場合。
* 決まらない型変数に適当な型を割り当てて先に進む（defaulting）方式も検討した。
  パラメトリシティにより、決まらない型変数の値は実行時に作られないので、どの型を割り当てても結果は変わらない。
  しかし、エラーにしておけば後から defaulting に緩められる（逆は既存のプログラムを壊す）ので、v0.3 ではエラーとする。

エラーメッセージに現れる、まだ決まっていない単一化変数は `?T`（`T` は元の型パラメータの名前）と表示する。

### 明示的な型引数を導入しない理由

* 引数・期待される型・後の使い方のどれかから型引数が決まらない場面は、`let` に型注釈を付ければ解消できる。
* 導入するなら、構築子（`None[Int]`）や関数値（`let f = identity[Int]`）にも書けるようにする必要があり、構文と型検査の両方が膨らむ。
* 次の段階で型推論を強めるので、明示的な型引数が必要な場面はさらに減る。
  必要になった時点で、別の ADR で追加する。

### let は単相のまま

`let f = identity` と書くと、`f` の型は `?T -> ?T` になり、以降の使い方で 1 つの型に決まる。
`f(1)` と `f(true)` を両方書くと型エラーになる。
`let` で束縛した値を多相にする（一般化する）のは、ADR-0001 の成長過程の「let 多相」の段階で扱う。

### 値の表現: 型引数の表現ごとの特殊化

多相な値の表現として、次の案を比較した。

| 案 | 概要 | v0.3 で採用しない / する理由 |
| --- | --- | --- |
| A. 完全な単相化（Rust、MLton） | 型引数の組ごとに関数を複製する | IR と ABI はそのまま使える。しかし、型引数の組の数だけ関数が増える。多相再帰（`f[T]` の中で `f[List[T]]` を呼ぶ）は無限に展開されるので、検出してエラーにする必要がある |
| B. 一様表現（OCaml、Haskell、Java の型消去） | 多相な値をすべて `i64` の枠やヒープ上の箱に入れ、関数を 1 つだけ作る | 関数が増えない。しかし、多相な関数との境界で `i32` と `i64` の変換が必要になり、関数値を渡すときは変換用のラッパー関数を生成する必要がある。すべての値を `i64` にすれば変換は要らないが、v0.1・v0.2 の ABI とゴールデンテストをすべて変えることになる |
| C. 辞書渡し（Go の GC shape stenciling と辞書） | 表現ごとに関数を作り、型に依存する操作は実行時の辞書で行う | v0.3 には型に依存する操作（型パラメータの値の比較、表示など）がないので、辞書は不要 |
| **D. 型引数の表現ごとの特殊化（採用）** | 型引数を IR の値型（`Int`、`Bool`、`FuncRef`、`Ptr`）に写し、その組ごとに関数を 1 つ作る | 下記 |

**採用する方式（D）**:

* 多相な関数は、型引数の組そのものではなく、**各型引数の IR の値型の組**ごとに 1 つの IR 関数へ特殊化する。
  * 例: `identity[Int]` と `identity[Bool]` は別の関数になる。
    `identity[List[Int]]`、`identity[Option[Bool]]`、`identity[Shape]` は、型引数がすべて `Ptr` なので、同じ 1 つの関数 `identity[Ptr]` を共有する。
  * 型パラメータの値の中身を調べる操作がないので、多相な関数の本体から生成する IR は、型引数の値型だけで決まる。
    同じ値型の組に対しては、同じ IR が生成される。
* データ型は特殊化しない。
  ADR-0003 のブロックのレイアウトは、フィールドの型にかかわらず各フィールドを 8 バイトの枠に入れ、タグは構築子の宣言順で決まる。
  そのため、`List[Int]` と `List[Bool]` はレイアウトとタグが同じで、違いはフィールドを `i64` として読み書きするか `i32` として読み書きするかだけである。
  その違いは、構築と照合を行う場所（特殊化された関数の中）で、具体的な値型として IR に現れる。
* プログラムの実行時には、すべての型引数が具体的な型に決まっている。
  同じ具体的な型は常に同じ値型に写るので、値を書き込む側と読み出す側の値型は必ず一致する。
* 特殊化は、IR 生成（`internal/lower`）で、`main` を含む多相でない関数から到達する組だけを行う。
  どこからも使われない多相な関数は、型検査だけ行い、IR にも WebAssembly にも出力しない。
  多相でない関数は、v0.2 と同じくすべて出力する。

採用する理由:

* **ABI とバックエンドが変わらない。** IR のノードと値型は v0.2 のままで、WebAssembly バックエンド（`internal/wasm`）は変更しない。
  ADR-0002・ADR-0003 の値の表現の表は v0.3 でもそのまま成り立つ。
  多相な関数の中の型パラメータ `T` の値は、その特殊化の型引数の表現（`i64` または `i32`）で表される。
* **特殊化の数が有限で、多相再帰を扱える。** 値型は 4 種類なので、型パラメータが n 個の関数の特殊化は最大で 4^n 個である。
  `f[T]` の中で `f[List[T]]` を呼んでも、`List[T]` は常に `Ptr` なので、特殊化 `f[Ptr]` が自分自身を呼ぶだけで展開が止まる。
  完全な単相化（案 A）のような、多相再帰の検出とエラーは要らない。
* **変換とラッパーが要らない。** 一様表現（案 B）のような、境界での値の変換や、関数値を渡すときのラッパー関数の生成が不要である。
* **型検査と IR 生成の分担が単純になる。** 型検査は多相な関数を 1 回だけ検査し、各参照の型引数を記録する。
  IR 生成は、型パラメータから値型への対応表を持って本体を変換するだけでよい。

値型の組をさらに WebAssembly の型（`i64` と `i32` の 2 種類）まで縮める案も検討した。
しかし、IR は `Bool` と `Ptr` を区別する型付きの表現であり（`lower` はノードの IR の型と型検査の型の一致を確かめている）、それを崩す利点が小さいので採用しない。

### エラー報告

ADR-0002 のとおり、最初に見つけたエラー 1 件だけを報告する。

## Consequences

* `Option[T]`、`List[T]`、`map`、`foldl` などの汎用の型と関数を書けるようになる。
  `IntList` のような要素型ごとの宣言は不要になる。
* 関数の引数と戻り値の型注釈は引き続き必須で、`let` は単相のままである。
  `let f = identity` の `f` を 2 つの型で使うことはできない。これは let 多相の段階で解消する。
* 型引数を推論できない式（`let x = None` を使わない場合など）は、型注釈を付ける必要がある。
* 型パラメータの値は比較も照合もできない。型パラメータの値を比較したい場合（たとえば汎用の `contains`）は、比較関数を引数で受け取る。
  型に依存する操作を言語に入れる（type class など）ときは、辞書渡しか完全な単相化を検討し直す必要がある。
* **関数は特殊化の数だけ複製される。** 型パラメータが n 個の関数は最大 4^n 個になる。
  匿名関数は、それを含む関数の特殊化ごとに持ち上げられる。
* **分割コンパイルとの関係**: 特殊化はプログラム全体を見て行う。
  module を導入するときは、多相な関数の本体を module の境界を越えて参照できるようにする（あるいは別の表現に切り替える）必要があり、module の ADR で扱う。
* **GC との関係**: データ型を特殊化しないので、ブロックのフィールドがポインタかどうかは、型ではなく構築した場所の値型で決まる。
  将来の GC がフィールドのポインタの位置を必要とするなら、構築時にブロックのヘッダ（ADR-0003 のオフセット 4 の未使用の 4 バイトなど）へ記録する方法がとれる。方式は GC の ADR で決める。
* **クロージャとの関係**: 関数値の表現をクロージャ用に変えても、関数値の値型が 1 種類（`FuncRef`）であることは変わらないので、特殊化の方式には影響しない。
* **x86-64 バックエンドとの関係**: 特殊化は IR 生成で終わるので、IR から先のバックエンドは多相を意識しなくてよい。
* 型、型検査、IR 生成に変更が及ぶ。WebAssembly バックエンドは変更しない。
  設計書は `docs/design/v0.3-frontend.md`、`docs/design/v0.3-typecheck.md`、`docs/design/v0.3-backend.md` に分け、この順に実装する。
