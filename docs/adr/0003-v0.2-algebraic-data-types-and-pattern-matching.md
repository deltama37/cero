# ADR-0003: v0.2 の代数的データ型・パターンマッチ・ヒープ表現

* Status: Accepted
* Date: 2026-09-24

## Context

v0.1 は ADR-0001 の Initial Goal（`fib(10)` のコンパイルとローカル実行）を達成した。
ADR-0001 の Development Policy では、v0.1 の次の段階を「代数的データ型、pattern matching、String / List」としている。

この段階に進むには、v0.1 にはない次の点を決める必要がある。

* どこまでを 1 つのバージョンに含めるか
* `type` 宣言と `match` 式の具体構文
* パターンの種類と、網羅性をどこまで検査するか
* 値を WebAssembly でどう表現するか
  v0.1 の値は `i64` と `i32` だけで、線形メモリを使っていない（ADR-0002）。
  代数的データ型の値は、複数のフィールドを持つのでメモリ上に置く必要がある。
* 確保したメモリをどう回収するか
  GC は ADR-0001 で v0.1 の対象外としている。

## Decision

### v0.2 の範囲

v0.2 では、単相の代数的データ型と、それに対する `match` 式だけを導入する。

* 型パラメータ（`Option[T]` など）は導入しない。
  ADR-0001 の成長過程では、パラメトリック多相は代数的データ型の次の段階にある。
  そのため、リストは `IntList` のように要素型ごとに宣言する。
* String と、組み込みの List / Array は v0.2 に含めない。
  どちらもヒープ表現と回収の方針に強く依存するので、v0.2 の運用を見てから別の ADR で決める。
* `main` の型は v0.1 と同じ `() -> Int` とする。

### `type` 宣言

```text
type Shape =
    | Circle(Int)
    | Rect(Int, Int)

type IntList =
    | Nil
    | Cons(Int, IntList)
```

* `type` 宣言はトップレベルにだけ書ける。関数宣言と任意の順に並べられる。
* 構文は `type Name = | Ctor | Ctor(T1, ..., Tn) ...` とする。先頭の `|` は省略できる。
* 構築子（コンストラクタ）は 1 つ以上必要とする。構築子のない型は宣言できない。
* 構築子のフィールドは型だけを書く。フィールド名（レコード）は導入しない。
* フィールドの型には `Int`、`Bool`、関数型、宣言したデータ型を書ける。
* 型は宣言順に関係なく互いに参照できる。自分自身や互いを参照する再帰型を許す。
* 型名と構築子名は ASCII の大文字で始める。そうでなければ構文エラーとする。
* 型名は、ほかの型名や `Int`、`Bool` と重複できない。
* 構築子名は、すべての型をまたいで一意とし、トップレベル関数名とも重複できない。
* 引数や `let` で、構築子と同じ名前の変数を束縛することはできない。

### 値の構築

* フィールドを持つ構築子は、関数呼び出しと同じ形で `Circle(3)`、`Cons(1, Nil)` と書く。引数の個数と型は検査する。
* フィールドを持たない構築子は、`Nil` のように名前だけで書く。`Nil()` は型エラーとする。
* 構築子は第一級の値ではない。`let f = Circle` のように、呼び出さずに値として使うことはできない。
  必要なら `fn(r: Int) -> Shape { Circle(r) }` と書く。
* データ型の値に `==` と `!=` は使えない（ADR-0002 のとおり、比較できるのは `Int` 同士と `Bool` 同士だけ）。

### `match` 式

```text
fn area(s: Shape) -> Int {
    match s {
        Circle(r) => 3 * r * r,
        Rect(w, h) => w * h,
    }
}

fn sum(xs: IntList) -> Int {
    match xs {
        Nil => 0,
        Cons(x, rest) => x + sum(rest),
    }
}
```

* 構文は `match 式 { パターン => 式, ... }` とする。
* 各アームは `,` で区切る。最後のアームの後の `,` は省略できる。
  ADR-0002 では文の区切り記号を導入しなかったが、アームの区切りは明示する。
  区切りがないと、将来負の整数パターンやタプルパターンを追加したときに、前のアームの式と続けて解釈されうるため。
  検討した代替案は次のとおり。
  * 区切りなし（ADR-0001 の例の書き方）: v0.2 のパターンの範囲なら曖昧にならないが、上記の理由でパターンを増やせなくなる。
  * 各アームを `|` で始める（`| Nil => 0 | Cons(x, rest) => ...`）: `type` 宣言と記号が揃い、曖昧さもない。
    ただし、アームの本体の式が長いときに次のアームの始まりが見えにくく、`,` 区切りのほうが広く使われているので採用しない。
  * 改行を区切りにする: ADR-0002 で改行を空白と同じに扱うと決めているので採用しない。
* `match` は式であり、`if` と同じく式を書ける場所ならどこにでも書ける。
  照合対象の式の直後に `{` が来たときの扱いは、`if` の条件式と同じ規則に従う。
* アームは 1 つ以上必要とする。
* すべてのアームの式は同じ型を持ち、それが `match` 式の型になる。
* 照合対象の型は `Int`、`Bool`、宣言したデータ型のいずれかとする。関数型の値は照合できない。
* 実行時には、アームを上から順に試し、最初に一致したアームの式を評価する。

### パターン

v0.2 で使えるパターンは次のとおり。

| パターン | 例 | 一致する値 |
| --- | --- | --- |
| ワイルドカード | `_` | 任意の値。何も束縛しない |
| 変数 | `x` | 任意の値。`x` に束縛する |
| 構築子 | `Nil`、`Cons(x, _)` | その構築子で作られた値 |
| 整数リテラル | `0`、`42` | その整数 |
| 真偽値リテラル | `true`、`false` | その真偽値 |

* 構築子パターンの引数には、変数と `_` だけを書ける。構築子パターンの入れ子（`Cons(x, Cons(y, _))`）は v0.2 では書けない。
  入れ子の照合は、`match` を入れ子にして書く。
* 負の整数リテラルはパターンに書けない。
* パターン中の名前は、大文字で始まれば構築子、そうでなければ変数として扱う。
  大文字で始まる名前が構築子として宣言されていなければ、型エラーとする。
* 1 つのパターンの中で同じ変数を 2 回束縛することはできない。
* パターンで束縛した変数のスコープは、そのアームの式だけとする。外側の同名の変数を隠せる（`let` と同じ）。
* `_` 単独は予約語とし、式や `let`、引数の名前には使えない。`_x` のように `_` で始まる名前は、これまでどおり識別子とする。

### 網羅性と到達不能なアーム

コンパイラは次を検査し、違反があればコンパイルエラーとする。

* **網羅性**: どのアームにも一致しない値がありうる `match` は、エラーとする。
  * データ型では、ワイルドカードか変数のアームがない限り、すべての構築子のアームが必要。
    エラーメッセージには、足りない構築子の名前を宣言順に並べる。
  * `Bool` では、`true` と `false` の両方か、ワイルドカードか変数のアームが必要。
  * `Int` では、ワイルドカードか変数のアームが必要。
* **到達不能なアーム**: それより前のアームだけで、そのアームに一致するすべての値が捕まる場合は、エラーとする。
  ワイルドカードや変数のアームの後に続くアームや、同じ構築子・同じリテラルが 2 回目に現れるアームが該当する。

ADR-0002 のとおり、エラーは最初の 1 件だけを報告する。v0.2 には警告の仕組みがないので、到達不能なアームも警告ではなくエラーとする。

構築子パターンの入れ子を許さないので、この検査は「アームの先頭のパターンの集合」を見るだけで行える。
入れ子を許すときは、パターン行列に対する usefulness の判定などの一般的なアルゴリズムが必要になる。これは後続の ADR で扱う。

### WebAssembly での表現

| Cero の値 | WebAssembly の表現 |
| --- | --- |
| `Int` | `i64`（v0.1 と同じ） |
| `Bool` | `i32`（v0.1 と同じ） |
| 関数値 | `i32` の funcref テーブルのインデックス（v0.1 と同じ） |
| データ型の値 | `i32`。線形メモリ上のブロックの先頭アドレス |

データ型の値のブロックは、次のレイアウトとする。

| オフセット | 内容 |
| --- | --- |
| 0 | タグ（`i32`）。構築子の、型の中での宣言順の番号（0 始まり） |
| 4 | 未使用（4 バイト） |
| 8 + 8 × i | i 番目のフィールド（8 バイト） |

* ブロックの大きさは `8 + 8 × フィールド数` バイトとし、先頭アドレスは 8 の倍数に揃える。
* フィールドは型にかかわらず 8 バイトの枠に入れる。`Int` は `i64` として、それ以外は `i32` として枠の先頭 4 バイトに格納する。
  フィールドの位置が型によらず決まるので、コード生成が単純になる。
* フィールドを持たない構築子の値も、呼び出すたびに 8 バイトのブロックを確保する。
  静的領域に 1 つだけ置く最適化は、後で行ってもよい。
* アドレス 0 はブロックとして使わない。ヒープはアドレス 8 から始める。

### メモリの確保と回収

* モジュールは線形メモリを 1 つ定義する。メモリは import もエクスポートもしない。
  ADR-0002 の「import を持たない、WASI を使わない」は v0.2 でも維持する。
* 確保は、ヒープの次の空き位置を指すミュータブルなグローバル変数を進めるだけの、バンプアロケータで行う。
  空きが足りなければ `memory.grow` でメモリを増やし、増やせなければトラップする。
* **v0.2 では確保したメモリを回収しない。** メモリはプログラムの終了時にまとめて解放される。

回収しない理由は次のとおり。

* v0.2 のプログラムは、`main` が値を 1 つ返して終わる短命な計算であり、実用上の問題になりにくい。
* GC の方式は、String、クロージャ、IO / Effect の表現と、将来の x86-64 バックエンドのランタイムに依存する。
  これらが決まる前に作ると、作り直しになる可能性が高い。
* Cero 製 `ceroc` は大量に確保するので、self-hosting より前には回収の方針を決める必要がある。これは後続の ADR で扱う。

WebAssembly の GC 提案（WasmGC）の構造体型を使う案は、採用しない。

* 固定している wasmtime 25.0.3 では、GC 提案の構造体型を含むモジュールを実行できない。
  既定では検証で拒否され、`-W gc=y,function-references=y` を指定しても `struct.new` が未実装としてエラーになる。
  使えるバージョンに上げたとしても、`ceroc run` の呼び出し方と利用者の実行手順にフラグが必要になる。
* 型セクションに再帰型グループや参照型を書く必要があり、v0.1 のエンコーダからの変更が大きい。
* 将来の x86-64 バックエンドでは、いずれ独自のメモリ管理が必要になる。
  線形メモリ上の表現は、その設計にそのまま持ち込める。

## Consequences

* 型パラメータがないので、`Option[T]` のような汎用の型は書けず、要素型ごとに型を宣言する必要がある。
  パラメトリック多相を導入するときに、データ型の宣言と型検査を拡張する。
* 構築子パターンを入れ子にできないので、深い構造の照合は `match` を入れ子にして書くことになり、冗長になる。
* 名前の先頭が大文字かどうかで、パターン中の構築子と変数を区別する。構築子や型の名前に小文字始まりは使えない。
* `_` 単独と、`type`、`match` が予約語になるので、v0.1 でこれらを名前に使っていたプログラムはコンパイルできなくなる。
* メモリを回収しないので、確保を繰り返す長い計算では、メモリを使い切ってトラップしうる。
* 線形メモリとグローバル変数を使うので、WASM バックエンドにメモリセクションとグローバルセクションの出力が加わる。
  バンプアロケータを、モジュール内の補助関数として生成する必要もある。
* 実装は、既存のフロントエンド、型検査、IR、WASM バックエンドのすべてに変更が及ぶ。
  設計書は `docs/design/v0.2-*.md` として、v0.1 と同じ単位に分けて書く。
