# ADR-0008: v0.6 のクロージャ（外側の変数の捕捉）と関数値の表現

* Status: Accepted
* Date: 2026-10-06

## Context

ADR-0001 は「v0.1 ではクロージャが外側の変数を捕捉する機能は必須としない」とし、v0.1〜v0.5 では、匿名関数から外側の引数・`let`・パターン変数を参照すると型エラーにしていた。
ADR-0002 は関数値を funcref テーブルのインデックス（`i32`）で表し、「クロージャを導入するときは表現を変える必要がある」とした。

v0.3 以降は `map(xs, f)` のような高階関数を書けるが、`f` から外側の値を使えないので実用性が低い。
Cero 製 ceroc を書く段階では、環境（型環境、名前表）を引き回す関数を部分的に適用する場面が多い。
ADR-0004 は「関数値の表現をクロージャ用に変えても、値型が 1 種類（`FuncRef`）であることは変わらないので、特殊化の方式には影響しない」と予告している。
ADR-0006 は「匿名関数の中から一般化した `let` を参照できるようにするかを、クロージャの ADR で扱う」とした。

## Decision

### 範囲

匿名関数は、外側の関数の引数、`let`、パターン変数（一般化した `let` を含む）を参照（捕捉）できる。

```text
fn makeAdder(n: Int) -> Int -> Int {
    fn(x: Int) -> Int { x + n }
}

fn scale(xs: List[Int], k: Int) -> List[Int] {
    map(xs, fn(x) { x * k })
}
```

* 値は不変なので、捕捉は値のコピーで行う。参照で捕捉した場合と区別できない。
* 局所的な関数の再帰（`let rec`）は導入しない。`let` の右辺から、その `let` 自身の名前は見えない（v0.1 のまま）。再帰はトップレベルの関数で書く。
* 関数値の比較は引き続きできない（ADR-0002）。

### 関数値の表現: テーブルのインデックスと環境ポインタの組

関数値は 64 bit の値とし、下位 32 bit を funcref テーブルのインデックス、上位 32 bit を**環境**（捕捉した値を入れたヒープ上のブロック）のアドレスとする。

```text
FuncRef (i64) = env_ptr << 32 | table_index
```

* 環境のブロックは、ADR-0003 のデータ型の値と同じレイアウト（8 バイトのヘッダとタグ 0、続いて 8 バイトの枠に捕捉した値を 1 つずつ）で、同じバンプアロケータで確保する。
* 何も捕捉しない関数値（トップレベルの関数、捕捉のない匿名関数）は、環境のアドレスを 0 とし、ヒープを確保しない。
* テーブルに入るすべての関数は、利用者の引数の**後ろ**に環境のアドレス（`i32`）を受け取る。
  * 持ち上げた匿名関数は、本体の先頭で、環境から捕捉した値を局所変数に読み込む。
  * トップレベルの関数を値として使うときは、環境を無視してその関数を末尾呼び出しするだけのラッパー関数（`NAME$ref`）をテーブルに入れる。直接呼び出しは今までどおりラッパーを通らない。
* 関数値の呼び出しは、引数を積んだ後で関数値から環境のアドレスとインデックスを取り出し、`call_indirect`（末尾位置なら `return_call_indirect`）で呼ぶ。

検討した案:

| 案 | 概要 | 採用しない / する理由 |
| --- | --- | --- |
| A. クロージャのブロックへのポインタ（OCaml など） | 関数値はヒープ上のブロック `[コード, 捕捉した値...]` のアドレス（`i32`） | 捕捉のないトップレベルの関数を値にするたびに確保するか、静的なブロックをデータセグメントに置く必要がある。呼び出しのたびにメモリからインデックスを読む |
| **B. インデックスと環境ポインタの組（採用）** | 上記 | 捕捉のない関数値は確保しない。データ型のフィールドは 8 バイトの枠なので、`i64` の関数値をそのまま格納できる。値型は `FuncRef` の 1 種類のまま |
| C. 非関数化（defunctionalization） | 関数値をタグつきのデータにし、呼び出しを `match` にする | プログラム全体の変換が必要で、分割コンパイル（module）と相性が悪い |

### 一般化した `let` の捕捉

ADR-0006 は、一般化した `let` を参照のたびに右辺から IR にし直すと決めた。右辺が外側の変数を捕捉する匿名関数でも、この方式をそのまま使う。

* 一般化した `let` の右辺が捕捉する変数は、その `let` を参照する匿名関数も捕捉する（捕捉する変数の集合を、参照をたどって推移的に求める）。
* 変数は不変で、宣言ごとに別の名前（シンボル）なので、参照の場所で右辺を IR にし直しても、定義の場所と同じ値を指す。

### WebAssembly と ABI

* `FuncRef` の WebAssembly の型を `i32` から `i64` に変える。ADR-0002・ADR-0003 の値の表現の表の `FuncRef` の行を置き換える。
* `main` のエクスポートと、`ceroc run` の動作は変わらない。

## Consequences

* `makeAdder` や、外側の値を使う `map` の引数を書けるようになる。
* 捕捉のある関数値を作るたびに、環境のブロックを確保する。ブロックは回収しない（ADR-0003 のメモリの方針のまま）。
* テーブルに入る関数のシグネチャが、利用者の型より引数が 1 つ多くなる。トップレベルの関数を値として使うと、ラッパー関数が 1 つ増える。
* **GC との関係**: 関数値の上位 32 bit がポインタになる。将来の GC がポインタの位置を必要とするなら、`FuncRef` の値は上位 32 bit をポインタとして扱う必要がある。GC の ADR で扱う。
* **x86-64 バックエンドとの関係**: 同じく、インデックス（関数表の番号）と環境のアドレスを 64 bit にまとめる表現を使える。アドレスが 32 bit を超える環境では表現を見直す。
* 型検査は捕捉のエラーを取り除くだけである。IR 生成（捕捉の解析、環境の構築と読み込み、ラッパー）と WebAssembly バックエンド（`i64` の関数値、呼び出し規約）に変更が及ぶ。
