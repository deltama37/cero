# ADR-0006: v0.4 の let 多相と匿名関数の型推論

* Status: Proposed
* Date: 2026-10-01

## Context

v0.3 でパラメトリック多相と単一化を導入した（ADR-0004）。
ADR-0001 の Development Policy では、その次の段階を「let 多相、型推論」としている。
ADR-0004 は次の 2 点をこの段階に先送りした。

* let 多相: `let f = identity` の `f` は単相で、`f(1)` と `f(true)` を両方書くと型エラーになる。
* 関数の引数と戻り値の型の推論: 型注釈を必須としている。

この段階に進むには、次の点を決める必要がある。

* 型注釈を省略できる場所（匿名関数か、トップレベルの関数も含むか）
* let で束縛した値を一般化する（多相にする）条件
* 多相になった let の値を、ADR-0004 の「型引数の表現ごとの特殊化」でどう表現するか
* 型注釈がない値に対して、呼び出し・`match`・`==` をどう型付けするか
* 推論できなかった型の扱いと、エラーメッセージでの表示

本 ADR でこれらを決める。実装の詳細は `docs/design/v0.4-*.md` に書く。

## Decision

### v0.4 の範囲

v0.4 では、次の 2 つを導入する。

1. **匿名関数の型推論**: 匿名関数の引数と戻り値の型注釈を省略できるようにし、省略した型を単一化で決める。
2. **let 多相**: `let` の右辺が匿名関数か名前のとき、決まらずに残った型変数を一般化し、束縛した名前を使うたびに別の型で使えるようにする。

```text
type List[T] =
    | Nil
    | Cons(T, List[T])

fn map[T, U](xs: List[T], f: T -> U) -> List[U] { ... }

fn main() -> Int {
    let id = fn(x) { x }                      // id : forall t1. t1 -> t1
    let xs = map(Cons(1, Nil), fn(x) { x * 2 }) // x : Int
    let none = None                           // none : forall T. Option[T]
    if id(true) { id(40) + 2 } else { 0 }
}
```

v0.4 に含めないもの:

* **トップレベルの関数の型推論。** トップレベルの関数の引数と戻り値の型注釈は、引き続き必須とする（構文エラーのまま）。
  ADR-0001 の `fn identity(x) { x }` から `identity : a -> a` を導くことは、v0.5 で別の ADR として扱う。
  トップレベルの関数は互いに再帰できるので、推論には呼び出しの依存関係を強連結成分に分けて順に推論・一般化する仕組みが必要になる。
  また、型注釈がある関数でだけ多相再帰（ADR-0004）を許すかどうかの判断も要る。v0.4 の let 多相とは独立に決められるので、段階を分ける。
* クロージャ。匿名関数の中から外側の局所変数（一般化した `let` を含む）を参照する捕捉は、v0.1 と同じくエラーのままとする。
* 引数とパターン変数の一般化。Hindley–Milner と同じく、匿名関数の引数とパターン変数は単相とする。
* 決まらない型変数の defaulting（ADR-0004 と同じくエラーにする）、明示的な型引数（ADR-0004）、`==` を多相にするための type class。
* 一般化した `let` の名前の型を表示する手段（REPL や `ceroc` のサブコマンド）。

### 型注釈の省略（匿名関数）

* 匿名関数の引数は `fn(x, y: Int) { ... }` のように、引数ごとに `: 型` を省略できる。
* 戻り値の型は `-> 型` ごと省略できる。省略したときの戻り値の型は、本体の型である。
* 省略した引数の型は、新しい単一化変数とする。その変数は、本体の中の使い方と、匿名関数を渡した先の期待される型の両方から決まる。
* トップレベルの関数（`fn name(...)`）は、これまでどおり引数と戻り値の型注釈を必須とする。省略は構文エラーとし、エラーメッセージも変えない。

### 単一化変数を中心にした型付け（Hindley–Milner に向けた拡張）

型注釈のない値が増えると、型がまだ決まっていない値を呼び出したり照合したりする場面が出てくる。
v0.3 ではこれらをすべて「推論できない」エラーにしていたが、v0.4 では Hindley–Milner と同じく、その場の使い方から型を決める。

* **呼び出し**: 呼び出し対象の型が未解決の単一化変数なら、各引数の型を推論し、`(引数の型, ...) -> ?r`（`?r` は新しい単一化変数）と単一化する。
  `fn(f) { f(1) + 1 }` の `f` は `Int -> Int` になる。
* **`match`**: 照合対象の型が未解決の単一化変数なら、最初の「構築子のパターン・整数リテラル・真偽値リテラル」のアームから型を決める。
  構築子なら、そのデータ型に新しい単一化変数を型引数として適用した型（`Option[?T]` など）、整数リテラルなら `Int`、真偽値リテラルなら `Bool` とする。
  すべてのアームが `_` か変数なら、v0.3 と同じく推論できないエラーとする。
* **`==` / `!=`**: 左辺の型が未解決の単一化変数なら、先に右辺を左辺の型と単一化し、その後で比較できる型（`Int` か `Bool`）かを確かめる。
  `fn(x) { x == 1 }` の `x` は `Int` になる。`fn(x, y) { x == y }` は、型が決まらないので比較できないエラーとする（type class がないため）。

### let の一般化

`let` で束縛するとき、右辺が次のどちらかであれば一般化する。

* 匿名関数（`fn(x) { x }`）
* 名前（`identity`、`None`、一般化した別の `let` の名前など）

一般化では、右辺の型に残っている未解決の単一化変数のうち、**その時点でスコープにある局所的な名前（引数、`let`、パターン変数）の型に現れないもの**を、その `let` の型パラメータにする。

* 型パラメータは、右辺の型の中で最初に現れる順に並べる。名前は元の単一化変数の名前（`T`、`t1` など）を使う。
* 一般化した `let` の名前を参照するたびに、v0.3 の多相な関数と同じくインスタンス化し、型引数を単一化で決める。
* 一般化できる変数が 1 つもなければ、v0.3 と同じ単相の `let` になる。`let x = 1` や `let f = fn(x: Int) -> Int { x }` の扱いは変わらない。
* `let` の型注釈は、一般化より先に右辺と単一化する。注釈は型パラメータを書けないので、`let n: Option[Int] = None` は単相になる。
* 型パラメータを持つ外側の関数の型パラメータ（硬い型変数）は一般化しない。外側の関数の型パラメータとして、そのまま残る。

右辺がそれ以外の式（呼び出し、`if`、`match`、ブロックなど）なら一般化せず、v0.3 と同じく単相とする。
`let g = identity(fn(x) { x })` の `g` は単相で、`g(1)` と `g(true)` を両方書くと型エラーになる。

### 一般化する右辺を制限する理由（値の表現との関係）

ADR-0004 は、多相な値を「型引数の表現ごとの特殊化」で表すと決めた。
多相な関数は、使われる値型の組ごとに別の IR 関数になる。
すると、一般化した `let` の値も、1 つの実行時の値として持つことはできない。`let id = fn(x) { x }` を `id(1)` と `id(true)` で使うには、`i64` 版と `i32` 版の 2 つの関数が要るからである。

そこで、**一般化した `let` は、その場では評価せず、名前を参照するたびに右辺をその型引数で IR にする**。
右辺が匿名関数なら、参照ごとに特殊化した関数を持ち上げて関数値にする。右辺が名前なら、参照ごとにその名前（多相な関数なら特殊化した関数）の値にする。

この方式が正しいのは、右辺が匿名関数か名前だからである。

* 匿名関数と名前の評価は、必ず停止し、副作用がなく、ほとんど計算しない。何回評価しても、評価しなくても、結果は変わらない。
* 関数値どうしは比較できない（ADR-0002）ので、参照ごとに別の関数値ができても観測できない。

検討した他の案:

| 案 | 概要 | 採用しない理由 |
| --- | --- | --- |
| A. どんな右辺も一般化し、参照ごとに再評価する | 制限なし | Cero は正格評価なので、評価の回数と停止性が変わる。使わない `let x = loop()` が停止するようになり、重い計算は参照の数だけ繰り返される |
| B. どんな右辺も一般化し、値型の組ごとに `let` の場所で 1 回ずつ評価する | 参照より先に、使われる値型の組を集めて評価する | 評価の回数と順序が、型（値型の組の数）に依存する。IR 生成が「参照を集めてから `let` を変換する」2 段階になり複雑になる |
| C. 一様表現に切り替える | 多相な値を 1 つの表現で持つ | ADR-0004 で採用しなかった。ABI とバックエンドを変える必要がある |
| **D. 右辺が匿名関数か名前のときだけ一般化する（採用）** | ML の value restriction に相当する構文的な制限 | 上記のとおり、評価の意味を変えずに既存の特殊化だけで実装できる |

OCaml などの value restriction は、可変な参照があるときの型安全性のための制限である。
Cero は純粋なので型安全性のためには不要だが、値の表現（特殊化）のために同じ形の制限を置く。
制限は後から緩められる（既存のプログラムは壊れない）ので、必要になれば案 B を別の ADR で検討する。

### 決まらなかった型

ADR-0004 と同じく、トップレベルの関数 1 つの本体を検査し終えた時点で、未解決の単一化変数が残っていればエラーとする。一般化した変数は解決済みとして扱う。

| 単一化変数を作った場所 | メッセージ |
| --- | --- |
| 多相な名前のインスタンス化（v0.3） | `cannot infer type argument 'T' of 'NAME'; add a type annotation` |
| 型注釈を省略した匿名関数の引数 | `cannot infer the type of parameter 'x'; add a type annotation` |
| 型が未解決の値の呼び出しの結果 | `cannot infer the result type of this call; add a type annotation` |
| `match` の照合対象の型引数 | インスタンス化と同じ（`NAME` は構築子の名前） |

v0.3 では `let x = None` で `x` を使わないとエラーだったが、v0.4 では `x` が一般化されるのでエラーにならない。

### 型の表示

* 型注釈を省略した引数と、呼び出しの結果のために作る単一化変数は、トップレベルの関数ごとに作った順に `t1`、`t2`、… と名付ける。未解決のときは `?t1` と表示する。
* インスタンス化で作る単一化変数は、v0.3 と同じく元の型パラメータの名前（`?T`）で表示する。
* 一般化してできた型パラメータは、元の単一化変数の名前（`t1`、`T`）で表示する。小文字で始まる型パラメータは、一般化でしかできない。

### エラー報告

ADR-0002 のとおり、最初に見つけたエラー 1 件だけを報告する。

## Consequences

* `fn(x) { x * 2 }` のように、匿名関数の型注釈を書かなくてよくなる。多相な関数に渡す匿名関数は、渡した先の型から引数の型が決まる。
* `let id = fn(x) { x }` や `let f = identity`、`let none = None` を複数の型で使えるようになる。
* 一般化するかどうかは右辺の形で決まる。`let g = identity(fn(x) { x })` は単相のままなので、利用者は「右辺が匿名関数か名前なら多相」という規則を知っておく必要がある。
* **IR の大きさ**: 一般化した `let` の右辺が匿名関数なら、名前を参照するたびに関数を 1 つ持ち上げる。同じ型引数の参照でも共有しない。
  プログラムの意味は変わらないが、IR と WebAssembly の関数の数が増える。必要になれば、型引数の表現ごとに共有する最適化を別途行う。
* 一般化した `let` は実行時の局所変数を持たない。使わなければ IR に何も出力しない。
* トップレベルの関数の型注釈は引き続き必須である。v0.5 でトップレベルの関数の型推論を導入するときは、構文（型注釈の省略）、相互再帰の依存解析、一般化を、本 ADR の仕組み（単一化変数の名前、一般化の手順）の上に追加する。
* クロージャを導入するときは、匿名関数の中から一般化した `let` を参照できるようにするかを、クロージャの ADR で扱う（参照ごとに右辺を IR にする方式は、捕捉がない右辺に限って成り立つ）。
* 構文解析・型検査・IR 生成に変更が及ぶ。IR のノードと値型、WebAssembly バックエンドは変更しない。
  設計書は `docs/design/v0.4-frontend.md`、`docs/design/v0.4-typecheck.md`、`docs/design/v0.4-backend.md` に分ける。
