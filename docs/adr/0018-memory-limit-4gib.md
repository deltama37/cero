# ADR-0018: WebAssembly のメモリの上限を 4 GiB 近くに上げる

* Status: Accepted
* Date: 2026-10-06

## Context

ADR-0003 は、メモリの最大を 32768 ページ（2 GiB）とした。理由は「ページ数 << 16 が符号なしの i32 に収まるように」である。
ADR-0010 は、self-hosting まではメモリを回収しないとし、ADR-0015 は「自己ビルドが 1.5 GiB を超えたら回収の方式の ADR を書く」とした。

`fmt`（ADR-0016）と LSP（ADR-0017）を加えた結果、Cero 製 ceroc の自己ビルドのピーク RSS は約 1.42 GB になった。
次の段階（x86-64 backend）で Cero 製 ceroc はさらに大きくなり、2 GiB の上限を超えて self-hosting が壊れるおそれがある。
LSP サーバも、Cero 製 ceroc 自身を開くと 1 回の解析で約 1.17 GiB を使う。

## Decision

### 上限を 65535 ページにする

メモリの最大を 65535 ページ（4 GiB − 64 KiB）にする。wasm32 のアドレス空間（4 GiB）のほぼ全体である。Go 製と Cero 製の両方を同じに変える（ADR-0014）。

* 65536 ページにしないのは、ページ数 × 65536 が 2^32 になり、符号なしの i32 に収まらないためである（65535 × 65536 = 0xFFFF0000 は収まる）。
* バンプアロケータ（`alloc`）の計算は i64 で行う。`heap + size` と、必要なページ数の計算が 2^32 を超えても桁あふれしない。上限を超える確保は、これまでどおり trap する。
* アドレスは符号なしの 32 bit として扱う。補助関数（文字列、IO）の中で、アドレスどうしを符号つきで比べている箇所があれば、符号なしの比較に直す。長さと添字（`Int` から来る値）の符号つきの比較はそのままでよい。

### 回収の ADR を書く目安

ADR-0015 の「自己ビルドが 1.5 GiB を超えたら」を、「自己ビルドが 3 GiB を超えたら」に置き換える。

* 理由: 上限が 2 倍になり、回収なしで続けられる余地も 2 倍になった。回収の方式は、表現（ADR-0003 のヘッダ、ADR-0008 の関数値）と 2 つのコンパイラ（ADR-0014）の全体に及ぶので、必要になるまで先送りする（ADR-0010 と同じ判断）。

検討した他の案:

| 案 | 採用しない理由 |
| --- | --- |
| Cero 製 ceroc の確保を減らす | 効果がどれだけあるか測らないとわからず、移植の忠実さ（ADR-0014）を崩す変更になりやすい。上限を上げても、後で行える |
| 回収（GC）を入れる | ADR-0010 の比較のとおり、全体に及ぶ大きな変更 |
| memory64 | 固定した wasmtime 25 では既定で使えず、ポインタの表現（ADR-0003、ADR-0008）を変える必要がある |

## Consequences

* 1 つのプログラムが確保できるメモリが、約 2 GiB から約 4 GiB になる。
* 出力するすべての WebAssembly のメモリのセクションと `alloc` の本体が変わる（動作は 2 GiB 未満では同じ）。
* ホストの仮想メモリの予約は wasmtime が 4 GiB 単位で行うので変わらない。実際に使うメモリは確保した分だけである。
* x86-64 backend（次の段階）のヒープの上限も、同じ 4 GiB 近くとする。
