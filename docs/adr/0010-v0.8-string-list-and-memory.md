# ADR-0010: v0.8 の String、List の扱い、メモリ回収の方針

* Status: Accepted
* Date: 2026-10-06

## Context

ADR-0001 の成長過程は、代数的データ型・パターンマッチと同じ段階に「String / List」を置いている。
ADR-0003 は「String と、組み込みの List / Array は v0.2 に含めない」「Cero 製 ceroc は大量に確保するので、self-hosting より前には回収の方針を決める必要がある」とした。
ADR-0004 は、`List` / `Option` を組み込みにするかどうかを、この ADR に先送りした。

Cero 製 ceroc（ソースの読み込み、識別子、エラーメッセージ、WebAssembly のバイト列の出力）と LSP（ADR-0001）は String を必要とする。

## Decision

### String

`String` を組み込みの型として追加する。

* 値は不変のバイト列とする。ソースの文字列リテラルは UTF-8 のバイト列としてそのまま入れる。
  文字（コードポイント）の型は導入せず、1 バイトは `Int`（0〜255）で扱う。長さと添字はバイト単位とする。
  Cero 製 ceroc が扱うソースは ASCII が中心で、UTF-8 の解釈が必要になった時点で、バイト列の上にライブラリとして書ける。
* 文字列リテラル `"..."` を書ける。エスケープは `\n`、`\t`、`\r`、`\\`、`\"`、`\0`、`\xHH`（16 進 2 桁のバイト）とする。リテラルの中の改行はエラーとする。
* 演算子:
  * `a ++ b`: 連結。優先順位と結合性は `+` と同じ。オペランドは両方 `String`。
  * `a == b`、`a != b`: バイト列としての等値比較。`String` を比較できる型に加える（ADR-0002 の `Int` と `Bool` に加える）。
* 組み込み関数（トップレベルの関数と同じく、呼び出しも値としての使用もできる）:

| 名前 | 型 | 意味 |
| --- | --- | --- |
| `stringLength` | `(String) -> Int` | バイト数 |
| `stringByteAt` | `(String, Int) -> Int` | 添字のバイト（0〜255）。範囲外は実行時エラー |
| `stringSlice` | `(String, Int, Int) -> String` | `[start, end)` のコピー。`0 <= start <= end <= 長さ` でなければ実行時エラー |
| `stringFromByte` | `(Int) -> String` | 1 バイトの文字列。0〜255 でなければ実行時エラー |
| `stringCompare` | `(String, String) -> Int` | 辞書順（バイトを符号なしで比べる）で -1、0、1 |
| `intToString` | `(Int) -> String` | 10 進表記 |

* 組み込み関数の名前のトップレベルの関数・構築子は宣言できない。局所的な名前（引数、`let`、パターン変数）は、トップレベルの関数と同じく組み込み関数の名前を隠せる。
* パターンに文字列リテラルを書ける（`match kw { "fn" => ..., _ => ... }`）。照合はバイト列の等値比較で、網羅性の検査では整数と同じく、リテラルの集合は完全にならない。
* 実行時エラーは WebAssembly の trap（`unreachable`）とする。Cero には例外がない（ADR-0001）。

### String の表現

* `String` の値は、ヒープ上のブロックのアドレス（IR の `Ptr`、`i32`）とする。ブロックは、オフセット 0 に長さ（`i32`）、オフセット 4 は未使用、オフセット 8 からバイト列を置き、全体を 8 バイトの倍数に切り上げる。
  ADR-0003 のデータ型のブロックとヘッダの大きさをそろえ、将来の GC がヘッダを同じ形で扱えるようにする。
* 文字列リテラルは、WebAssembly のデータセグメントに同じレイアウトで置く（同じ内容のリテラルは 1 つにまとめる）。リテラルの評価はアドレスの定数で、確保しない。
  ヒープはデータセグメントの後ろから始める。
* 連結・切り出し・数値の変換は、新しいブロックを確保してバイト列をコピーする。
  文字列の操作は WebAssembly の補助関数（バンプアロケータと同じく、コンパイラが生成する）で実装する。

### List と Option は組み込みにしない

`List` と `Option` は組み込みの型にせず、v0.8 ではこれまでどおり利用者が宣言する。

* 理由: 組み込みにすると、利用者が宣言した同名の型（既存のサンプルと E2E のすべて）と衝突し、名前の解決に特例が要る。
  多相（ADR-0004）とクロージャ（ADR-0008）があるので、利用者の宣言で十分に書ける。
* 次の段階（module）で、`List`、`Option` と、その上の `map`・`foldl` などを、Cero で書いた標準ライブラリの module として提供する。標準ライブラリの置き場所と読み込み方は module の ADR で決める。
* 組み込み関数は `List` に依存させない。大きな文字列を作るときは、文字列の木（`type Doc = Text(String) | Concat(Doc, Doc)` など）を作り、出力するときにたどる書き方を想定する。

### メモリ回収: self-hosting までは回収しない

ヒープは、ADR-0003 のバンプアロケータで確保したまま回収しない。`memory.grow` で最大 2 GiB（ADR-0003 の上限）まで伸ばし、確保できなければ trap する。

* 理由:
  * Cero のプログラムは、`main` を 1 回呼んで終わるバッチ処理である。Cero 製 ceroc も、ソースを読んで WebAssembly を書き出したら終わるので、プロセスの終了がメモリの回収になる。
  * Go 製 ceroc の 1 回のコンパイルで確保する量は、ソースの大きさに比例する（数万行で数百 MB 以下の見込み）。
  * 回収の方式は、データの表現（ブロックのヘッダ、関数値の上位 32 bit のポインタ、ADR-0008）と強く結びつき、実装の量も大きい。必要になる前に決めると、表現の変更のたびに作り直すことになる。
* 検討した方式:

| 方式 | 概要 | 採用しない理由（今の段階で） |
| --- | --- | --- |
| 参照カウント（Perceus、Koka） | 純粋な言語では循環が作れないので回収できる。確保と解放の位置をコンパイラが決める | IR に所有権と解放の命令を入れる必要があり、全段に変更が及ぶ |
| トレース型 GC（シャドウスタックで根を記録） | 一般的な方式 | WebAssembly の値スタックは走査できないので、局所変数の根をメモリ上のスタックに書き出すコードが要る |
| WasmGC | ランタイムの GC を使う | ADR-0003 と同じ理由（固定した wasmtime で使えない、x86-64 バックエンドと共有できない） |
| **回収しない（採用）** | 上記 | 足りなくなった時点で、測定に基づいて別の ADR で方式を決める |

* self-hosting で Cero 製 ceroc が 2 GiB に収まらない場合は、その時点で回収の ADR を書く。

## Consequences

* 文字列を扱うプログラムを書けるようになる（`main` の戻り値は `Int` のままなので、出力は IO の段階で行う）。
* 文字列の連結は、そのたびに両方をコピーする。繰り返し連結するとコピーの量が 2 乗で増えるので、大きな文字列は木を作ってから出力する。
* 範囲外の添字は実行時に trap する。`Option` を返す安全な版は、標準ライブラリで Cero の関数として書ける。
* `List` と `Option` は、module の段階までは利用者が宣言する。
* メモリは回収しない。長く動くプログラム（LSP サーバ）を作る段階では、回収の方式を決め直す必要がある。
* 字句解析（文字列リテラル、`++`）、構文解析、型検査（`String`、組み込み関数、文字列のパターン）、IR（文字列の定数と組み込みの操作）、IR 生成、WebAssembly バックエンド（データセグメント、補助関数）に変更が及ぶ。
