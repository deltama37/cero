# ADR-0011: v0.9 の module と標準ライブラリ

* Status: Accepted
* Date: 2026-10-06

## Context

ADR-0001 の成長過程では、型推論の次の段階が「module」である。
これまでの Cero のプログラムは 1 つのファイルで、`List` や `map` を使うプログラムはそれぞれ自分で宣言していた。
ADR-0010 は、`List` と `Option` を組み込みにせず、module の段階で Cero で書いた標準ライブラリとして提供すると決めた。
ADR-0004 は「module を導入するときは、多相な関数の本体を module の境界を越えて参照できるようにする（あるいは別の表現に切り替える）必要があり、module の ADR で扱う」とした。

Cero 製 ceroc は数千行になる見込みで、字句解析・構文解析・型検査・コード生成を別のファイルに分けたい。

## Decision

### module とファイル

* 1 つのファイルが 1 つの module である。
* プログラムは、`ceroc build` / `ceroc run` に渡したファイル（**エントリ module**）と、そこから `import` でたどれる module の全体である。`main` はエントリ module に置く。
* module の名前（**module パス**）は、`/` で区切った名前の列である（`lexer`、`syntax/ast`、`std/list`）。各要素は ASCII の英数字と `_` だけからなる。

### import

```text
import "std/list"
import "syntax/ast"

pub fn parse(src: String) -> List[Ast] { ... }
```

* ファイルの先頭（型と関数の宣言より前）に `import "module パス"` を並べる。
* `std/` で始まる module は標準ライブラリで、ceroc に埋め込んだソースから読む。
* それ以外の module パス `p` は、**エントリ module のファイルがあるディレクトリ**からの相対パス `p.cero` のファイルとする。どの module から import しても同じファイルを指す（import する側のディレクトリには依存しない）。
* import は推移的ではない。`a` が `b` を import しても、`a` を import した module から `b` の名前は見えない。
* import の循環はエラーとする（相互再帰する関数は 1 つの module に置く）。
* 同じ module を 1 つのファイルで 2 回 import するとエラーとする。

### 公開と名前の解決

* `pub fn` と `pub type` だけが、他の module から見える。`pub type` は、その型のすべての構築子も公開する。構築子ごとの公開は導入しない。
* import した module の公開された名前は、**修飾なし**でそのまま使える（`map(xs, f)`、`Cons(1, Nil)`、`List[Int]`）。
  修飾した名前（`list.map`）は導入しない。式の構文（`.`）と名前の解決の両方が膨らみ、Cero 製 ceroc でも実装の手間が増えるため。必要になれば別の ADR で追加する。
* 名前の解決の優先順位（値の名前と型の名前のそれぞれ）は、局所的な名前 → その module のトップレベルの宣言 → import した名前 → 組み込み関数、とする。
  module 自身の宣言は import した名前を隠す（エラーにしない）。標準ライブラリに名前が増えても、既存のプログラムが壊れないようにするため。
* 2 つの import が同じ名前（値か型）を公開しているときは、後の import の位置で「`name` が `a` と `b` の両方から import されている」エラーとする。
* 公開する関数の型に非公開の型が現れてもエラーにしない（利用者はその型の名前を書けないだけ）。

### 型検査とコード生成

* module を import の依存順（import される側が先）に型検査する。module の間に循環がないので、トップレベルの関数の型推論（ADR-0007）は module ごとに行える。
* 型検査とコード生成はプログラム全体で行う（分割コンパイルはしない）。ADR-0004 の特殊化は、別の module の多相な関数も、そのまま使う側の型引数で特殊化する。
* エントリ module の多相でない関数は、v0.8 までと同じくすべて出力する。それ以外の module の関数は、使われたものだけを出力する（標準ライブラリの使わない関数で出力を大きくしない）。
* コンパイルエラーには、エラーのある module のファイル名（標準ライブラリなら `std/list.cero`）を付ける。

### 標準ライブラリ

v0.9 では、次の module を Cero で書いて提供する。リポジトリの `std/` に置き、Go の `embed` で ceroc に埋め込む（外部依存は増えない）。

| module | 内容 |
| --- | --- |
| `std/list` | `List[T]`（`Nil` / `Cons`）、`length`、`map`、`filter`、`foldl`、`foldr`、`reverse`、`append`、`concat`、`any`、`all`、`range`、`sum`、`take`、`drop` |
| `std/option` | `Option[T]`（`None` / `Some`）、`withDefault`、`mapOption`、`isSome`、`isNone` |
| `std/pair` | `Pair[A, B]`（`Pair`）、`fst`、`snd` |
| `std/string` | `join`、`startsWith`、`endsWith`、`isDigit`、`isAlpha`、`isSpace`（バイトの分類） |

関数の正確な一覧と型は設計書で決める。標準ライブラリへの追加は、言語の変更ではないので ADR を必要としない。

## Consequences

* プログラムを複数のファイルに分け、標準ライブラリの `List` / `Option` を使える。
* 名前は修飾なしで取り込むので、import の組み合わせによっては名前の衝突を解消するために module を分け直す必要がある。
* 1 つの import の追加で、プログラム全体の再コンパイルが要る（分割コンパイルなし）。Cero 製 ceroc の規模（数千行）では問題にならない見込み。
* 既存の 1 ファイルのプログラムは、そのまま動く（`pub` と `import` は省略できる）。
* 字句解析（`import`、`pub`）、構文解析、型検査（module ごとの名前の表）、IR 生成（複数のファイル、使われた関数だけの出力）、ドライバ（module の読み込み）、CLI に変更が及ぶ。WebAssembly バックエンドは変更しない。
