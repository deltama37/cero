# ADR-0009: v0.7 の入れ子のパターンと usefulness による網羅性検査

* Status: Accepted
* Date: 2026-10-06

## Context

ADR-0003（v0.2）は、構築子パターンの引数に変数と `_` だけを許し、入れ子の照合は `match` を入れ子にして書くとした。
網羅性と到達不能なアームの検査は「アームの先頭のパターンの集合」を見るだけで行い、
「入れ子を許すときは、パターン行列に対する usefulness の判定などの一般的なアルゴリズムが必要になる。これは後続の ADR で扱う」とした。

Cero 製 ceroc（ADR-0001）は、トークン列や構文木を `match` で分解するコードが大部分になる。
`Cons(Token(LParen, _), rest)` のような入れ子のパターンがないと、`match` の入れ子が深くなり、書くのも読むのも難しい。
ADR-0001 の成長過程にはない段階だが、Cero 製 ceroc の前提として v0.7 で導入する。

## Decision

### 範囲

構築子パターンの引数に、任意のパターン（`_`、変数、構築子、整数リテラル、真偽値リテラル）を書けるようにする。

```text
fn second(xs: List[Int]) -> Int {
    match xs {
        Cons(_, Cons(y, _)) => y,
        _ => 0,
    }
}

fn both(p: Pair[Bool, Bool]) -> Int {
    match p {
        Pair(true, true) => 3,
        Pair(true, false) => 2,
        Pair(false, _) => 0,
    }
}
```

v0.7 に含めないもの:

* or パターン（`A | B`）、ガード（`if` 条件）、as パターン（`x @ Cons(...)`）、範囲パターン
* 負の整数リテラルのパターン（ADR-0003 のまま）
* `let` の左辺のパターン（`let Pair(a, b) = p`）

### 型付け

* 構築子パターンの各引数は、そのフィールドの型（データ型の型引数を代入したもの）で型検査する。
  フィールドの型が未解決の単一化変数なら、`match` の照合対象と同じく（ADR-0006）、引数のパターン（構築子・整数・真偽値）から決める。
* 1 つのパターンの中で同じ変数を 2 回束縛できない規則は、入れ子の全体に適用する。

### 網羅性と到達不能なアーム: usefulness

Maranget の「パターン行列の usefulness」（*Warnings for pattern matching*, 2007）で判定する。

* アーム i のパターンが、それより前のアームのパターンの行列に対して useful でなければ、到達不能なアームのエラーにする。
* すべてのアームの行列に対して `_` が useful なら、網羅していないエラーにする。
* 構築子の集合が完全かどうかは、データ型のすべての構築子、`Bool` の `true` と `false` で判定する。`Int` のリテラルの集合は完全にならない。
* 判定は型の情報を使わず、パターンが指す構築子（構築子はデータ型を知っている）とリテラルの種類だけで行う。

エラーメッセージは、網羅していない値の例（witness）をパターンの構文で示す。

* 先頭の列で、どのアームにも現れない構築子・真偽値がある（かつワイルドカードや変数のアームがない）場合は、v0.2 と同じく、それらをすべて宣言順に並べる。
  フィールドを持つ構築子は `Circle(_)` のように `_` を付ける。
  例: `non-exhaustive match: missing Circle(_), Square(_, _)`
* それ以外は、例を 1 つ示す。例: `non-exhaustive match: missing Cons(_, Cons(_, _))`
* 整数の部分は `_` で示す（「ほかの整数」を意味する）。例: `non-exhaustive match: missing Some(_)`
* 到達不能なアームのメッセージは v0.2 と同じ `unreachable match arm` とする。

ADR-0003 のメッセージ（`non-exhaustive match: Circle, Square`、`Int values need a '_' or variable pattern`）は、上の形式に置き換える。

### 実行時の照合

* 平らなパターン（v0.2 で書けた形）だけの `match` は、v0.2 と同じくタグによる分岐（`SwitchTag`）にする。生成するコードは変わらない。
* 入れ子のパターンを 1 つでも含む `match` は、アームを上から順に試す。各アームのパターンを「タグの比較とリテラルの比較の論理積」に変換し、一致したアームで変数を束縛して本体を評価する。
  フィールドは、そのフィールドを持つ構築子であることを確かめた後でだけ読む（論理積を短絡評価にする）。
  最後のアームは比較しない（網羅性により、それより前に一致しなければ必ず一致する）。
* 決定木への変換（同じ値のタグを 2 回読まない最適化）は行わない。必要になれば別途行う。

## Consequences

* `Cons(x, Cons(y, rest))` や `Pair(true, _)` のような照合を 1 つの `match` で書ける。
* 網羅性のエラーメッセージの形式が変わる（`missing` と例のパターン）。
* 入れ子のパターンを含む `match` では、同じ値のタグを複数のアームで読み直すことがある。プログラムの意味は変わらない。
* 構文解析・型検査（パターンの型付け、usefulness）・IR 生成を変更する。IR のノードと WebAssembly バックエンドは変更しない（タグの比較は既存の `SwitchTag` で表せる）。
